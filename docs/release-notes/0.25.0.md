# OpenFrame 0.25.0

OpenFrame now supports cached video alongside images. Upload MP4, MOV, or WebM files in Media, choose Economy (720p) or Quality (1080p), and insert the finished video through Add media. The server converts uploads to silent H.264 MP4 with a WebP poster, at most 30 fps, without upscaling. Sources are limited to 100 MiB and 60 seconds; optimized videos must fit 25 MiB. One conversion worker and a bounded queue keep processing resource use controlled. Originals are discarded after conversion, so retain your source files separately.

Player **0.11.0** downloads and verifies videos and posters before switching publications, then plays them from local storage. Multiple players can loop independently without repeated server downloads; playback is not synchronized across screens. The 256 MiB cache budget protects the current publication while downloading an update. Each slide supports one active video, poster-only preparation, and Cut transitions around video. Playback failures show the poster and report an error while allowing the playlist to advance. See [video support](../video-support.md) for limits, operation, and device acceptance.

This milestone also completes a project health review. Upload field limits and rollback handling prevent oversized multipart requests and orphan files after failed saves. Font deletion preserves consistent metadata, player font faces are released when unused, and the editor ignores stale font loads. Pi API responses now have the same 4 MiB bound as Android while preserving cached playback on rejection. Unused generator dependencies and obsolete release automation were removed; dependency updates resolve the five advisories found during review. CI now includes dependency auditing, FFmpeg checks, selected Chromium regressions, and Android JVM tests. The [maintenance punchlist](../maintenance-punchlist.md) records the completed work and remaining acceptance.

## Upgrade and rollback

Back up the complete database and media volume before updating. Pull the versioned 0.25.0 image or the successfully published `latest` image, then recreate the server container while preserving its data volume and Compose project name. Image publication does not update a running server automatically. The container includes FFmpeg and ffprobe; direct Node installations need both tools for video conversion. Allow the 100 MiB source limit plus multipart overhead in any reverse proxy. Unfinished conversion jobs must be retried after a server restart.

**Update players to 0.11.0 before publishing or assigning video playlists.** Android updates must use the existing signing key and require user-confirmed installation. Update the complete Pi player installation, including its shared renderer. Video publications use manifest schema 5; older players reject them and retain their last usable cached publication. Playlists without video keep schemas 2, 3, or 4 as appropriate, and updated players continue accepting older schemas. Existing accounts, media, and publications remain usable without a manual migration.

Video playback on physical Onn and Pi devices remains **experimental**. Automated checks do not establish hardware decoding, thermals, dropped-frame behavior, or unattended reliability. Complete the Onn/Pi offline restart and 24-hour playback checks before relying on video for unattended displays.

To return to server 0.24.0, select its versioned image and restore the pre-upgrade data backup for a consistent rollback without unsupported video layers or assets. Save any newer content separately before restoring. Updated players remain compatible with the older server. If downgrading players too, first remove all video layers, including removed-media placeholders, and republish compatible playlists while the updated server is available. Rolling back an image alone does not undo content changes or restore deleted files.

## Verification

Local verification of the accumulated changes passed **228 Node tests, 97 Python tests, 33 native Java tests, and ten Chromium suites**, including real Python-agent integration, video conversion and playback, uploads, fonts, and workspace regressions. A clean frozen-lockfile install, lint, typecheck, production build, version/repository checks, compatibility review, and Pi shell syntax checks pass. Both full and production dependency audits report zero known vulnerabilities at review time; the audited package count fell from 529 to 301.

An adapted local AMD64 container build mounts the managed environment CA only during networked build steps. Isolated runtime checks cover login, real video optimization, poster/media integrity, container replacement, and stopped-volume backup/restore. These results do not establish native ARM64 or physical-device acceptance.

The version tag gates image publication on hosted CI and native AMD64/ARM64 container verification; the main-branch player version change separately triggers signed Android publication. The [milestone workflows](https://github.com/veRoduS/OpenFrame/actions) record those results. Verify both workflows before assuming the registry `latest` image or latest APK has advanced. Signed APK installation and physical Onn/Pi acceptance remain outstanding.
