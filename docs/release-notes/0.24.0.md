# OpenFrame 0.24.0

Applications can now receive one API key and create their own feeds and metrics by pushing named JSON values to `POST /api/data-feeds/ingest/{sourceKey}`. New fields are created on any successful push, including later updates. Omitted fields retain their values; existing field types remain fixed. Each application has its own source namespace, managing group and keys. Admins can generate, rotate, expire and revoke keys in Settings. Invalid writes leave the previous data and schema intact. Disabling, demoting or deleting the issuing admin stops ingestion.

Use the [API one-pager](../data-feeds-api-one-pager.md) for request format, a Mac/Linux terminal example, update behavior, supported values, limits and error handling. The [full API guide](../data-feeds-api.md) and additive OpenAPI 1.1 contract cover both application ingestion and existing feed-specific integrations. Legacy keys and complete-snapshot PUT requests remain supported.

Slides now show compact Tags and Access controls with hover previews and click-to-edit dialogs. The Assigned indicator removes the physical-display disclaimer, and single-layer slides say “1 layer.” Users & Groups hides the built-in admin from its user list, allows direct group membership editing from a user's Groups tab, and offers confirmed user deletion. Media adds Small/Medium/Large grid sizes. Screens preserve their order across heartbeats and offer Row/Grid views.

## Upgrade and rollback

Back up the complete database and media volume before updating. Pull the versioned 0.24.0 image or the successfully published `latest` image, then recreate the server container while preserving its data volume and Compose project name. Image publication does not update a running server automatically.

Application registration, keys and source mappings use additive database tables created automatically at startup. No manual metric migration is required. Existing accounts, feeds, slide bindings and publications remain usable. Bind an automatically created metric to a slide and publish the layout once; subsequent values arrive through normal player sync without republishing.

Player 0.10.14 and manifest schema 4 are unchanged. No player upgrade is required for these server changes; data widgets still require player 0.10.13 or newer. Physical Pi/Android performance has not been revalidated for this milestone.

Rolling back to 0.23.0 removes application-key management and ingestion endpoints; new integrations will need to pause until the server is upgraded again. Restore the pre-upgrade data backup when a full data rollback is required. Account deletion is permanent and is not undone by rolling back the server image.
